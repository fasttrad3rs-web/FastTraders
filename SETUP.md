# Development setup

Getting Fast Traders running locally against real services, start to finish.

Budget about 40 minutes. Everything here is on a free tier — no card required
for any of it.

**Rule for this whole document: these are *your* development accounts.** The
client's production accounts get created separately, on his email, before
launch. Never point local development at his live database or his shop inbox —
a retry loop in a bug can send fifty emails to Sharjeel in under a minute.

At any point you can run:

```bash
npm run doctor
```

It connects to each service for real and tells you exactly which credential is
wrong and where to fix it. Use it after every step below.

---

## 0. Prerequisites

```bash
node --version    # must be v20 or higher
npm --version     # v10+
```

If Node is older, install v20 LTS from nodejs.org or via `nvm install 20`.

Then, from the repo root:

```bash
npm install
```

This installs both workspaces. It takes a few minutes the first time.

## 1. MongoDB Atlas — the database

### 1.1 Create the account

1. Go to **cloud.mongodb.com** → *Try Free*
2. Sign up with **your own** email (not the client's)
3. When it asks about your goal, any answer is fine — it only affects tips

### 1.2 Create the cluster

1. Choose **M0 Free** — 512 MB, permanently free
2. Provider: **AWS**. Region: **Mumbai (ap-south-1)** — closest to Pakistan,
   so you are not debugging latency that will not exist in production
3. Cluster name: `fast-traders-dev`
4. **Create Deployment**. Provisioning takes 3–5 minutes

### 1.3 Create the database user

Atlas usually prompts for this immediately. If not: **Database Access** →
*Add New Database User*.

- Username: `ftdev`
- Password: click **Autogenerate Secure Password**, then **Copy** it
- **Paste it somewhere safe right now.** You cannot see it again
- Role: **Read and write to any database**

> **Trap:** if you type your own password and it contains `@ : / ? # [ ] %`,
> the connection string will break, because those are URL-reserved characters.
> Use the autogenerated one, or stick to letters and digits.

### 1.4 Allow your IP

**Network Access** → *Add IP Address* → **Allow Access From Anywhere**
(`0.0.0.0/0`) → Confirm.

Yes, that is open to the world — but the database still requires the username
and password, and this is a development cluster with junk data in it. The
alternative is re-adding your IP every time your ISP rotates it, which is the
single most common reason people spend an hour on "connection timed out".

Production gets a locked-down allowlist. This one does not need it.

### 1.5 Get the connection string

**Database** → *Connect* → **Drivers** → Node.js.

**Copy the string from Atlas — do not copy the example below.** The part after
your cluster name (`ab1cd` here) is a random suffix unique to your account, so
the line printed in this document will never resolve. This is the single
easiest mistake to make on this page.

Yours will look like this, with a different suffix:

```
mongodb+srv://ftdev:<db_password>@fast-traders-dev.XXXXX.mongodb.net/?retryWrites=true&w=majority
```

Two edits are required:

1. Replace `<db_password>` with the password from 1.3 — **including deleting
   the angle brackets**
2. Insert the database name after `.net/` and before the `?`

Final form:

```
mongodb+srv://ftdev:YOUR_PASSWORD@fast-traders-dev.XXXXX.mongodb.net/fast_traders_dev?retryWrites=true&w=majority
```

> Miss the database name and Mongo silently uses one called `test`. Everything
> appears to work, and then you cannot find your data. `npm run doctor` prints
> the database name it connected to — check it says `fast_traders_dev`.

## 3. Mailtrap — the email sandbox

Mailtrap catches every email your app sends and shows it in a web inbox.
Nothing is delivered to a real person, which is precisely the point.

1. Go to **mailtrap.io** → *Sign Up*
2. Once in: **Email Testing** → **Inboxes** → open *My Inbox*
3. Find the **Integrations** dropdown → select **Nodemailer**

You get a snippet like:

```js
host: "sandbox.smtp.mailtrap.io",
port: 2525,
auth: { user: "a1b2c3d4e5f6g7", pass: "h8i9j0k1l2m3n4" }
```

Take the `user` and `pass`. Note the port is **2525**, not 587.

> Make sure you are in **Email Testing**, not *Email Sending*. Email Sending
> delivers to real inboxes and needs a verified domain. Testing is the sandbox.

## 4. Generate the JWT secrets

Two long random strings, and they must differ from each other.

**macOS / Linux:**

```bash
openssl rand -base64 48
openssl rand -base64 48
```

**Windows PowerShell:**

```powershell
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Max 256 }))
```

Run it twice. Keep both outputs.

> If the two are identical, a refresh token would be accepted as an access
> token — a real security hole. `npm run doctor` checks for this.

## 5. Write the environment files

### 5.1 Server

```bash
cd server
cp .env.example .env
```

Open `server/.env` and fill it in:

```bash
# 5050, not 5000: macOS AirPlay Receiver holds 5000 and the API cannot bind.
PORT=5050
NODE_ENV=development

# From step 1.5 — note the database name before the ?
MONGO_URI=mongodb+srv://ftdev:YOUR_PASSWORD@fast-traders-dev.XXXXX.mongodb.net/fast_traders_dev?retryWrites=true&w=majority

# From step 4 — two different strings
JWT_ACCESS_SECRET=paste_the_first_openssl_output_here
JWT_REFRESH_SECRET=paste_the_second_one_here
ACCESS_EXPIRY=15m
REFRESH_EXPIRY=7d

CLIENT_URL=http://localhost:3000

# From step 2
CLOUDINARY_CLOUD_NAME=dz1abcxyz
CLOUDINARY_API_KEY=123456789012345
CLOUDINARY_API_SECRET=your_api_secret
CLOUDINARY_FOLDER=fast-traders-dev

# From step 3 — Mailtrap, NOT Gmail
SMTP_HOST=sandbox.smtp.mailtrap.io
SMTP_PORT=2525
SMTP_SECURE=false
SMTP_USER=your_mailtrap_user
SMTP_PASS=your_mailtrap_pass
SMTP_FROM="Fast Traders <dev@fasttraders.co>"

# Where inquiry alerts go. In development this is caught by Mailtrap
# whatever you put, so use your own address, never the client's.
ADMIN_EMAIL=your.email@gmail.com
LOG_LEVEL=debug

# Pick your own admin password, or leave blank to have one generated
SEED_ADMIN_PASSWORD=ChangeMe123!
RATE_LIMIT_WINDOW_MS=900000
RATE_LIMIT_MAX=300
```

**Formatting rules that catch people out:**

- No spaces around `=` — `PORT=5050`, never `PORT = 5050`
- No quotes unless the value contains a space (`SMTP_FROM` needs them)
- No trailing spaces after a value
- No `#` comment on the same line as a value

### 5.2 Client

```bash
cd ../client
cp .env.example .env.local
```

The defaults are already correct for local work:

```bash
NEXT_PUBLIC_API_URL=http://localhost:5050/api/v1
NEXT_PUBLIC_SITE_URL=http://localhost:3000
NEXT_PUBLIC_WHATSAPP_NUMBER=923244234990
```

> The file is `.env.local`, **not** `.env` — Next.js only reads `.env.local`
> for local overrides. And `NEXT_PUBLIC_API_URL` must end in `/api/v1` or
> every request 404s.

### 5.3 Confirm neither file will be committed

```bash
cd ..
git status --short
```

Neither `server/.env` nor `client/.env.local` should appear. They are already
in `.gitignore`; this is just confirmation.

If either does show up, stop and fix `.gitignore` before committing anything.

## Step 12 in full: proving the Cloudinary uploads

Two separate upload paths exist, and they behave differently. Every automated
test stubs the network, so they prove our logic and nothing about Cloudinary's.
This is the only part of the system that has never touched the real API.

### 12.1 The automated check

```bash
npm run verify:cloudinary
```

It uploads a real 1×1 PNG and a real **two-page** PDF to your account, checks
what came back, downloads both again, and deletes everything it made. Nothing
is written to MongoDB.

A healthy run:

```
Cloudinary upload verification

1. Credentials
    OK   api.ping() answers — ok

2. Nameplate photo -> resource_type "image"
    OK   resource_type is image — image
    OK   landed in the right folder — fast-traders-dev/_verify/nameplate_xxx
    OK   URL is https — https://res.cloudinary.com/...
    OK   Cloudinary parsed it as a picture — 1x1
    OK   the stored file is reachable — HTTP 200
    OK   served as an image — image/png

3. Datasheet -> resource_type "raw"
    OK   resource_type is raw — raw
    OK   landed in the right folder — fast-traders-dev/_verify/datasheet_xxx
    OK   byte count preserved — 622 vs 622
    OK   the stored file is reachable — HTTP 200
    OK   bytes come back identical — 622 bytes back
    OK   both pages survived — a rasterised PDF would have lost page two

4. The same PDF sent as "image" — demonstrating the failure
    OK   it does NOT come back as the original PDF
         Cloudinary stored it as "pdf", 2 page(s), 1284 bytes.

5. Cleanup
    OK   removed fast-traders-dev/_verify/nameplate_xxx
    OK   removed fast-traders-dev/_verify/datasheet_xxx
    OK   removed fast-traders-dev/_verify/datasheet-as-image_xxx

Both upload paths work against the real Cloudinary account.
```

**Why step 4 is in there.** It demonstrates what `raw` actually buys, and it
earned its place by proving an earlier claim in this document wrong.

Cloudinary keeps the original bytes whichever resource type you use — a PDF
stored as `image` downloads back byte-identical, both pages intact. What
differs is afterwards: an `image` asset is *transformable*, so any URL carrying
a transformation returns a rendered picture of page one instead of the
document. A stray `f_auto`, a CDN rule or a helpful URL builder would hand
staff a screenshot of a customer's twelve-page datasheet. A `raw` asset has no
transformation surface at all.

Step 4 shows both halves: the untransformed URL returning the original, and the
same asset rasterised the moment a transformation is requested.

### The one almost everybody hits: PDF delivery is blocked

If step 3 reports `HTTP 401` on *reachable* while the upload itself passed, the
code is fine and the account is not. Cloudinary restricts **PDF and ZIP
delivery by default** on accounts created in the last few years — a response to
a past security advisory. The file uploads, stores and deletes normally; only
fetching it is refused.

The script proves this for you: when the PDF 401s it stores a plain `.txt` the
same way and fetches that. If the text file delivers and the PDF does not, the
restriction is on the format.

**Fix — Cloudinary Console:**

1. **Settings** (gear icon) → **Security**
2. Find **Restricted media types**
3. Untick **PDF** (and **ZIP**, if you want spreadsheets to open too)
4. **Save**, then re-run `npm run verify:cloudinary`

This is not optional for Fast Traders. Staff open a customer's datasheet from
the link in the alert email — with PDF restricted, every one of those links
returns 401 and the attachment is effectively lost. Do it on the **client's
production account** as well, not just your development one.

**What to do if a check fails:**

| Failure | Cause |
| --- | --- |
| Step 3 `HTTP 401`, `.txt` delivers | PDF delivery restricted. See above |
| Step 3 `HTTP 401`, `.txt` also fails | Raw delivery off account-wide, or the account is suspended or over quota |
| `cloud "scripts"` in the header line | The script is loading `scripts/env-setup.ts` instead of `.env`. It now refuses to run rather than blaming your credentials |
| `api.ping()` fails | Credentials. Re-copy all three from the dashboard; the cloud name is case-sensitive |
| `landed in the right folder` fails | `CLOUDINARY_FOLDER` differs from what you expect. Cosmetic, but fix it before production so the client's assets are not loose in the account root |
| `bytes come back identical` fails | The `raw` branch is broken. Attachments would be corrupted — stop and tell me |
| `removed …` fails | `destroy` needs the same `resource_type` as the upload. If this fails, delete the `_verify` folder by hand in the Media Library |

### 12.2 The manual check — admin product image

1. `/admin/products/new` → fill the tabs → **Save**
2. On the saved product, open the **Images** tab and upload a JPG or PNG
3. Cloudinary dashboard → **Media Library** → folder `fast-traders-dev/`
4. The file is there, and the thumbnail renders

Then view that product on the storefront: the image should appear, at a
sensible size, with no price anywhere on the page.

### 12.3 The manual check — sourcing attachments

This is the path that carries a customer's file, and it is the one worth doing
by hand at least once.

1. Open `/source-from-china`
2. Fill in the description, your name and a Pakistani mobile number
3. Attach **three** files:
   - a photo (JPG or PNG) — on a phone, use **Take a photo**
   - a PDF
   - **a renamed file**: copy any `.txt` to `photo.jpg` and attach that
4. Submit

Expect:

- The confirmation says **2 attachments received**
- It also says it could not read one file, naming `photo.jpg` and the reason
- In Mailtrap, the alert email shows the photo **inline** and the PDF as a link
- In Cloudinary, both are under `fast-traders-dev/sourcing/`
- The PDF link downloads the original file, all pages intact

The renamed file is the point of the exercise. Its extension and its
`Content-Type` both say JPEG — only its bytes say otherwise, and those are what
the server checks. If that file is accepted, the upload validation is not
working and you should stop and tell me.

## Troubleshooting

Every one of these is a real error message you may hit.

**`MongooseServerSelectionError: connection timed out`**
The IP allowlist. Atlas → Network Access → Add IP Address → Allow Access From
Anywhere. Takes about a minute to apply.

**`MongoServerError: bad auth : Authentication failed`**
Wrong password, or you left the `<` `>` brackets around it, or the password
contains a reserved character. Reset it in Atlas → Database Access with
*Autogenerate*.

**`querySrv ENOTFOUND _mongodb._tcp...`**
The cluster hostname is wrong — usually because the example address from this
document got copied instead of the real one from Atlas. The suffix after your
cluster name is unique to your account. Re-copy from Atlas → Connect →
Drivers.

**Data saved but you cannot find it in Atlas**
You omitted the database name from the URI, so it went to `test`. Add
`/fast_traders_dev` before the `?`.

**`Invalid Signature` from Cloudinary**
API secret is wrong or has a trailing space. Re-copy it from the dashboard.

**`Must supply api_key`**
`CLOUDINARY_API_KEY` is empty or misspelled in `.env`.

**`Invalid login: 535 Authentication failed` (SMTP)**
Mailtrap credentials wrong, or you copied them from *Email Sending* instead of
*Email Testing*. Port must be **2525**.

**`npm run doctor` says the API port is occupied**
If it reads *"5050 is our own dev server, already running"* that is a pass, not
a problem — doctor is safe to run with the app up. Only *"occupied but nothing
answers"* or *"held by something that is not this API"* needs action.

**`Error: listen EADDRINUSE :::5050`**
Something else already holds the port. Find out what:

```bash
lsof -i :5050
```

If the `COMMAND` is `node`, it is a dev server from an earlier run — `kill -9`
the PID. Anything else, change `PORT` in `server/.env` **and**
`NEXT_PUBLIC_API_URL` in `client/.env.local` together; changing one alone
means every request 404s.

This project deliberately avoids port 5000: on macOS, AirPlay Receiver
(`ControlCe` in `lsof`) listens there, and the failure looks like a code bug
rather than an occupied port.

**`[env] Invalid environment configuration` on boot**
The Zod check found a bad variable; it lists exactly which. Usually a typo, a
stray quote, or a value on the wrong line.

**CORS error in the browser console**
`CLIENT_URL` in `server/.env` must exactly match where the site is running —
`http://localhost:3000`, with no trailing slash.

**Storefront shows no products after a successful seed**
Check the API directly: `curl http://localhost:5050/api/v1/products?limit=2`.
If that returns data, the problem is `NEXT_PUBLIC_API_URL`. Restart the client
after changing it — Next.js only reads env at startup.

When you are ready to launch, repeat steps 1–3 with Sharjeel present, using
**fasttrad3rs@gmail.com**. He signs up and sets the passwords; he then invites
