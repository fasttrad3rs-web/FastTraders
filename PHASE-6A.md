# Phase 6A — Discovery pages, wired to the API

> **Superseded.** This document describes the site before the catalogue-only
> pivot — it still refers to prices, carts, checkout, payments, orders or
> customer accounts, none of which exist any more. Kept as build history.
> See [`CATALOG-PIVOT.md`](./CATALOG-PIVOT.md) for the current model.

33 new files. Every page below is a **Server Component** hitting the real
Phase 3 endpoints, with ISR at `revalidate: 300`.

| Route | What it does |
| --- | --- |
| `/` | 11 sections, all live data |
| `/products` | Faceted listing, URL-synced filters |
| `/products/[slug]` | Gallery, dual CTA, 5 tabs, Product schema |
| `/categories/[slug]` | Landing + subcategory chips + filtered grid |
| `/brands` · `/brands/[slug]` | Brand index and brand catalogue |
| `/sitemap.xml` · `/robots.txt` | Generated from live data |

## Data layer

`lib/api/endpoints.ts` — `serverFetch<T>()` wraps `fetch` with Next's data
cache. **It returns `null` instead of throwing**: a dead brand strip should
degrade the homepage, not blank it. Pages that genuinely need the data
(product detail) check for null and call `notFound()`.

`lib/api/catalog.ts` — one function per endpoint, all typed against the shared
`ApiResponse<T>` contract.

`lib/api/queries.ts` — the only client-side queries: the filter sidebar and
search autocomplete. Everything else is server-fetched. `keepPreviousData`
keeps the grid on screen while the next page loads rather than collapsing the
layout on a slow connection.

The homepage issues **one parallel wave** of six requests, so it costs the
slowest endpoint's latency rather than the sum.

---

## Filter state lives in the URL

`useCatalogFilters` reads and writes `searchParams` — no local filter state.
That makes every filtered view shareable and back-button friendly, which
matters when a buyer sends a colleague *"the 250 A MCCBs we looked at"*. The
server render and the first client query parse the **same** function, so they
cannot disagree.

`router.replace(..., { scroll: false })` keeps the shopper's place in the grid
when they tick a box.

## Hybrid commerce on the page

| `pricingMode` | Detail page shows |
| --- | --- |
| `retail` | Price · quantity · Add to Cart · Buy Now |
| `quote` | "Price on request" · quantity · note field · Request Quote |
| `both` | All of the above, quote framed as "Bulk / trade price?" |

**Ask on WhatsApp** is always present, pre-filled with the product name, SKU,
part number and chosen quantity — for many Pakistani trade buyers that is the
preferred channel, and it converts better than a form.

## SEO

`lib/seo/business.ts` carries the real business identity: Grace Tower address,
both phone numbers, geo coordinates, Mon–Sat 10:00–19:00 opening hours. This
is what feeds the Google Business panel for *"circuit breakers Lahore"*.

One `@graph` per page rather than loose script tags, so nodes cross-reference
by `@id` (Product → seller → Organization).

**Quote-only products publish no `offers.price`.** Advertising a price we do
not actually quote would be wrong, and it is a Merchant Center violation. They
still carry brand, SKU and MPN — which is what part-number searches hit.

`generateMetadata` on all three dynamic routes, with canonical URLs, Open
Graph and Twitter cards. Product keywords include the SKU and part number.

The sitemap flattens nested categories, pages products 100 at a time and caps
at 5000 so a growing catalogue cannot time the route out. Robots blocks
`/account`, `/cart`, `/checkout`, `/order-confirmation` and `/style-guide`.

## Images

Nine branded SVG placeholders in Fast Traders navy/cyan, one per top-level
category, generated by `scripts/generate-placeholders.mjs`. Local files, no
third-party placeholder service — `placehold.co` has been removed from
`next.config.mjs` entirely.

`<ProductImage>` overlays the SKU when the image is a placeholder, so a
catalogue awaiting photography still reads as a real product. When Sharjeel's
photos land on Cloudinary only the stored URL changes.

Every image goes through `next/image` with explicit `sizes`, `object-contain`
(industrial parts should never be cropped), and `priority` on the hero and the
first four grid cards.

## Bug found by the verification harness

Radix `Tabs` unmounts inactive panels, so the **specification table never
reached the server-rendered HTML**. On a site where buyers search
*"MCCB 250A 36kA"*, the specs are the single most valuable text on the page
and none of it was crawlable.

All five product tabs are now `forceMount`ed, with
`data-[state=inactive]:hidden` handling visibility. The content is in the HTML;
nothing is visible or focusable until its tab is selected.

## Verification

`tsc --noEmit` strict and `next lint` clean, no file over 300 lines, and all
ten app-router entries confirmed as Server Components.

A 14-check harness ran the real data layer against a mock API matching the
Phase 3 contract, then server-rendered the components and inspected the output:

- all seven endpoints resolve and populate
- home renders all 11 sections; map embed and both phone numbers present
- product detail renders the gallery, grouped specs and all five tabs
- cards show the correct CTA for each of the three pricing modes
- SKU overlay appears on placeholder images
- JSON-LD parses as a valid single `@graph` with all seven required types
- LocalBusiness carries address, geo and opening hours
- Product offer carries price, PKR, availability and a seller reference
- **quote-only products carry no offer** but keep their SKU
- BreadcrumbList starts at Home with sequential positions
- sitemap includes static, nested-category, brand and product URLs with no duplicates
- robots disallows every private area and references the sitemap

14/14 pass.

**Still not run:** `next build` (SIGBUS in this sandbox — a two-file Next app
fails identically) and Lighthouse, which needs a real browser against a real
server. The performance work is in place — Server Components by default,
44 of 98 files are client components and none of them are pages, ISR at 300s,
`next/image` with sizes throughout — but the 90+ target needs measuring
locally.
